Prompt Guide v3.0

控制思考，而不只是控制輸出

用 30 分鐘學會一套分層的 prompt 寫法：日常任務四行搞定，重要決策有完整閉環。

有效輸出 = Persona× Task× Context× Format

四項是相乘關係：任何一項空白，輸出品質都會明顯下降。最常被省略、也最影響結果的是 Context。

四層架構：依任務價值往上加

LEVEL 1｜核心層

Persona・Task・Context・Format

約 80% 的日常任務只需要這層。

LEVEL 2｜進階控制

Depth・Reasoning Mode・Constraint

想多深、怎麼想、邊界在哪。

LEVEL 3｜決策與驗證

Decision・Stress Test・Self-check

從分析走到可以拍板的結論。

LEVEL 4｜模板與知識

模板庫・Output SLA

每次都寫好，別人也能用。

30 秒範本

Persona：你是一位【角色】，讀者是【對象】
Task：請【動詞 + 具體目標】
Context：背景【…】；目標【…】；限制【…，因為…】
Format：【條列 / 表格 / Markdown】，【長度】

<document>
（要處理的資料）
</document>
Lesson 1

四要素：把 prompt 寫完整

點選下方每個要素，看看它控制什麼、怎麼寫。

前後對照：同一個需求，兩種寫法

✗ 模糊的 prompt
幫我重構這段程式碼。

模型不知道語言、問題在哪、要改到什麼程度、要什麼形式的結果，只能猜。

✓ PTCF prompt
Persona：資深後端架構師

Task：
1. 分析下方 Controller 的問題
2. 提出重構建議並附重構後程式碼

Context：
- Java Spring Boot 專案
- Controller 超過 800 行，同時處理驗證、
  業務邏輯與資料存取
- 目標是提升可維護性與可測試性

Format：
- 條列問題分析（標註違反的設計原則）
- 重構前後對照

<code>（貼上程式碼）</code>
小提醒：Persona 主要影響用語與觀點，不保證答案更正確。事實正確性靠的是 Context（提供資料）與 Level 3 的驗證。
Lesson 2

進階控制：想多深、怎麼想、邊界在哪

模組控制的是寫法範例
Depth洞察深度「請分析到系統設計層，並評估可擴展性；讀者有 3 年經驗。」
Reasoning Mode推理方式Few-shot、Chain of Thought、First Principles、Scenario Simulation
Constraint邊界條件「不使用商業資料庫，因為授權費超出預算。」

推理模型時代：還要寫「請逐步思考」嗎？

多數主流模型會在回答前自行思考。對這類模型，把力氣花在說清楚目標、判準與理由；需要更深入時，調高思考強度或寫「請仔細考慮邊界情況」。只有一般模型、或你需要看到推理過程時，才明確要求：

請先在 <thinking> 中列出推理步驟，再在 <answer> 中給出結論。

限制要附理由，不要加重語氣

✗ 加重語氣
嚴禁使用簡體字！！

新一代模型對指令很敏感，過度強調可能讓它在不相關的地方也過度套用。

✓ 附上理由
請使用繁體中文與台灣慣用術語，
因為讀者在台灣。

模型理解原因後，能推廣到沒列出的情況，例如用詞習慣。

Few-shot：範例要多樣，並用標籤包住

<examples>
<example>
<input>if (x == 'active') { doA(); } else { doB(); }</input>
<output>改用對照表或策略模式取代多重 if-else。</output>
</example>
</examples>
Lesson 3

決策閉環：從分析走到結論

只有分析、沒有結論的回答，常見症狀是「各有優缺點，視情況而定」。用 8 步驟把它變成可以拍板的報告：

Stress Test：這個結論在哪裡會崩？

規模

若流量成長 10 倍，哪裡先成為瓶頸？

假設

哪些假設可能是錯的？錯了會怎樣？

最壞情境

最壞情況是什麼？如何止損？

反方

最強的反對意見是什麼？

思維壓縮測試：請模型把結論濃縮成 150 字、30 字、一句話。一句話說不清楚，代表結論本身還不夠明確。

Self-check 的限制

同一次回答中的自我檢查效果有限，模型常會「確認」自己的答案。重要決策建議另開一次對話，請模型以審查者身份批評，或交由人工審核。
Lesson 4

模板與評估：讓好 prompt 可以重複

先定義「什麼叫做好」，才能驗收輸出、比較 prompt 版本。Output SLA 的五個面向可以直接當評分表：

面向1 分3 分5 分
清晰度讀完不知道結論結論清楚但需重讀一句話就能說清楚
邏輯一致性有明顯矛盾大致合理、有小跳躍每個結論都由前提推得
可執行性沒有具體建議有建議但缺順序有步驟、優先順序與負責人
風險揭露沒提風險列出風險但不完整含最壞情境與應對
假設透明度沒說明假設部分假設有說明明列假設與資料時間點

評估流程

定義成功標準 → 準備 5–20 個測試案例 → 跑出輸出 → 評分 → 一次只改一個變因 → 重跑比較

一次性的個人任務不需要這麼做；每週重複使用的 prompt、團隊共用模板與自動化流程才值得建立測試案例。

與時俱進

現代技巧速覽

用標籤組織 prompt

用 <document>、<instructions> 區隔資料與指令，多份文件時更不會混淆。

資料在前，問題在後

長文件放開頭、Task 放最後；並要求先引用原文再回答。

允許說不知道

「資料中沒有答案時請直接說明」，並要求標示來源與日期，降低幻覺。

Prompt Chaining

大任務拆成摘要 → 分析 → 產出 → 審查，每一步都能單獨檢查。

Meta-prompting

把 prompt 與不滿意的輸出一起交給模型，請它指出不清楚之處並改寫。

給 AI 代理的任務

寫清楚目標、範圍、驗收條件與限制，並要求它列出沒驗證到的部分。

目標：匯出報表時支援 CSV 格式。
範圍：只改 export/ 模組，不要動資料庫結構。
驗收：現有測試全過，並新增 CSV 匯出的測試。
限制：不新增第三方套件，因為新套件需經資安審核。
完成後請列出你沒有驗證到的部分。
