# Level 3｜決策與驗證層：Decision、Stress Test、Self-check

> 適用於要做決定的任務：技術選型、投資判斷、組織變革。目的是從「分析」走到「決策閉環」。

只有分析、沒有結論的回答，常見症狀是「各有優缺點，視情況而定」。Level 3 用三個模組避免這種空洞分析：

| 模組 | 回答的問題 | 控制的是 |
| --- | --- | --- |
| **Decision** | 所以我該怎麼做？ | 可行動性 |
| **Stress Test** | 這個結論在哪裡會崩？ | 穩健性 |
| **Self-check** | 推理本身有沒有漏洞？ | 品質穩定度 |

---

## 1. Decision：8 步決策閉環

1. **問題定義**：要決定的到底是什麼？成功標準是什麼？
2. **方案生成**：至少 2–3 種，包含「維持現狀」作為基準
3. **優缺點比較**：用一致的評估面向（成本、風險、時程、可維護性…）
4. **風險評估**：每個方案的主要風險與發生機率
5. **推薦方案**：明確選一個，並說明理由
6. **實作優先順序**：第一步做什麼、什麼可以延後
7. **壓力測試**：見下節
8. **自我檢查**：見下節

**寫法**

```text
請提供：
1. 可行方案（至少 3 種，含維持現狀）
2. 以表格比較優缺點（面向：成本、風險、學習曲線、時程）
3. 各方案的主要風險
4. 推薦方案與理由；若資訊不足以判斷，請說明還缺什麼
5. 實作優先順序
```

最後一句很重要：允許模型說「資訊不足」，可避免它為了給答案而編造前提。

---

## 2. Stress Test（壓力測試）

讓模型挑戰自己的結論，找出脆弱點。

| 類型 | 問法 |
| --- | --- |
| 規模 | 若流量／使用者成長 10 倍，哪裡先成為瓶頸？ |
| 假設 | 哪些假設可能是錯的？錯了會怎樣？ |
| 最壞情境 | 最壞情況是什麼？如何止損？ |
| 反方 | 最強的反對意見是什麼？ |
| 盲點 | 這個分析最可能漏掉什麼？ |
| 長期 | 哪裡會累積技術債或隱性成本？ |

**思維壓縮測試**：檢驗結論是否真的清楚。

```text
請把結論濃縮成 150 字版本，再給 30 字版本，最後給一句話版本。
```

若一句話版本說不清楚，代表結論本身還不夠明確。

## 3. Self-check（自我檢查）

要求模型在輸出前檢查自己的推理。

| 面向 | 檢查項目 |
| --- | --- |
| 邏輯 | 是否有推理跳躍？結論是否由前提推得？ |
| 證據 | 關鍵主張是否有資料支持？是否標註來源與日期？ |
| 簡化 | 是否過度簡化？是否忽略重要例外？ |
| 技術 | 是否有架構風險、安全漏洞、違反設計原則？ |
| 簡潔 | 是否有更簡單的做法？ |

> **限制**：同一次回答中的自我檢查效果有限，模型常會「確認」自己的答案。重要決策建議**另開一次對話**，把結果貼給模型並請它以審查者身份批評，或交由人工審核。評估方法見 [評估與迭代](07-evaluation-iteration.md)。

## 範例：SVN 轉 Git 的技術選型（完整閉環）

```markdown
Persona：資深架構師 + 專案經理

Task：提出版本控制升級方案並完成決策

Context：
- 背景：30 人團隊，目前使用 SVN
- 目標：導入 Git 並支援 CI/CD
- 限制：多數成員不熟 Git；遷移期間不能中斷發版

Format：比較表 + 建議方案（繁體中文）

Decision：
1. 可行方案（至少 3 種，含維持 SVN）
2. 優缺點比較（學習成本、工具整合、遷移風險、時程）
3. 風險評估
4. 推薦方案與理由
5. 實作優先順序

Stress Test：
- 若團隊不熟 Git，可能發生什麼問題（分支混亂、合併衝突）？
- 遷移過程如何確保歷史紀錄不遺失？
- 哪裡可能成為技術債？最壞情境是什麼？

Self-check：檢查是否有推理漏洞與未說明的假設
```

預期得到：一份可直接拿去開會的決策報告，而不是一般性的比較文章。同一份 prompt 的 JSON 版本見 [萬用模板](templates/general.md)。
