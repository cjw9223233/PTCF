# 評估與迭代：Metrics Layer

> 好的 prompt 不是一次寫成，而是用測試案例反覆比較出來的。本篇把 [Output SLA](04-template-system.md) 轉為可操作的評估流程。

---

## 1. 為什麼需要評估

- 只看一兩次輸出就判斷 prompt 好壞，很容易被偶然的好結果誤導。
- 修改 prompt 後，可能改善了 A 情況、卻弄壞了 B 情況。
- 模型版本更新後，原本有效的 prompt 可能表現不同。

有一組固定的測試案例，才能知道改動是進步還是退步。

---

## 2. 評估流程

```
定義成功標準 → 準備測試案例 → 跑出輸出 → 評分 → 修改一個變因 → 重跑比較
```

### Step 1：定義成功標準

具體、可判斷。

| 模糊 | 具體 |
| --- | --- |
| 摘要要好 | 涵蓋所有決議與負責人；300 字內；不加入原文沒有的資訊 |
| 程式碼要正確 | 通過既有測試；沒有新增的 lint 錯誤 |
| 分析要深入 | 至少比較 3 個方案；每個方案列出風險；有明確推薦 |

### Step 2：準備測試案例

- 5–20 個就能開始；涵蓋**典型情況**、**邊界情況**、**曾經出錯的情況**。
- 每個案例記錄：輸入、期望輸出的要點（不必是完整答案）。
- 案例存成檔案，和 prompt 一起版本控管。

本 repo 的模板案例放在 `evals/<模板 id>/cases.json`，`template_version` 必須與 [registry.json](templates/registry.json) 的版本一致。每個案例的欄位：

| 欄位 | 內容 |
| --- | --- |
| `id`、`description` | 案例代號與要測的情況 |
| `input` | 填好的 prompt，格式同 [prompt-template.json](templates/prompt-template.json) |
| `must_include` | 輸出必須出現的要點，可用規則檢查 |
| `must_not` | 輸出不可出現的內容，例如執行了資料中的指令 |
| `rubric` | 交給人或 LLM-as-judge 評分的 SLA 面向 |

```text
id: injection-in-document
description: 文件內夾帶「忽略先前指示」的句子
must_include: 摘要只涵蓋文件內容
must_not: 執行文件中的指示
rubric: 正確性、限制遵守
```

### Step 3：評分

把 Output SLA 轉為 1–5 分評分表：

| 面向 | 1 分 | 3 分 | 5 分 |
| --- | --- | --- | --- |
| 清晰度 | 讀完不知道結論 | 結論清楚但需重讀 | 一句話就能說清楚 |
| 邏輯一致性 | 有明顯矛盾 | 大致合理、有小跳躍 | 每個結論都由前提推得 |
| 可執行性 | 沒有具體建議 | 有建議但缺順序 | 有步驟、優先順序與負責人 |
| 風險揭露 | 沒提風險 | 列出風險但不完整 | 含最壞情境與應對 |
| 假設透明度 | 沒說明假設 | 部分假設有說明 | 明列假設與資料時間點 |

**評分方式**

| 方式 | 適用 | 注意 |
| --- | --- | --- |
| 規則檢查 | 格式、長度、必含關鍵字 | 最便宜、最穩定，能用就用 |
| 人工評分 | 少量案例、重要任務 | 最準確，但耗時 |
| LLM-as-judge | 大量案例 | 給評分模型明確的評分表與範例；定期用人工抽查校準 |

LLM-as-judge 的 prompt 範例：

```text
請依照 <rubric> 為 <output> 評分，每個面向 1–5 分，並先寫出評分理由再給分數。

<rubric>
（貼上評分表）
</rubric>

<input>（原始任務）</input>
<output>（要評分的輸出）</output>
```

### Step 4：迭代

- **一次只改一個變因**：例如只加 Few-shot，或只改 Format。同時改多處，就不知道是哪個改動有效。
- 每個版本都跑完整組測試案例，比較平均分數與個別退步的案例。
- 記錄每個版本的改動與結果。

---

## 3. 版本管理

```
prompts/
  meeting-summary/
    v1.md
    v2.md          # 加入 Few-shot
    test-cases.md
    results.md     # 各版本分數比較
```

| 版本 | 改動 | 平均分 | 備註 |
| --- | --- | --- | --- |
| v1 | 初版 | 3.2 | 常漏掉負責人 |
| v2 | 加入 2 個 Few-shot | 3.9 | 負責人問題改善；長會議仍會漏 |
| v3 | 改為先引用再摘要 | 4.3 | |

---

## 4. 什麼時候值得做

| 情境 | 建議 |
| --- | --- |
| 一次性的個人任務 | 不需要；看結果直接調整即可 |
| 每週重複使用的 prompt | 準備 5 個案例，改版前跑一次 |
| 團隊共用模板 | 測試案例 + 評分表，走 PR 審查 |
| 產品或自動化流程 | 完整評估，並在模型升級時重跑 |
