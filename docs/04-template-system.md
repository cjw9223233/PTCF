# Level 4｜模板與知識層：模板營運手冊

> 讓 Prompt 從個人技巧變成可重複、可分享、可驗收的團隊資產。

Level 1–3 解決「單次 prompt 寫得好」；Level 4 解決「每次都寫得好、別人也能用，而且模型換代後仍然有效」。

---

## 1. 場景模板庫

| 模板 | 層級 | 適用 |
| --- | --- | --- |
| [萬用模板](templates/general.md) | 1–3 | 任何任務；含極簡版、完整版、JSON 版 |
| [程式與專案模板](templates/programming.md) | 1–3 | 專案掃描、架構設計、重構、技術選型 |
| [投資分析模板](templates/investment.md) | 1–3 | 分析類 prompt 寫法示範（非投資建議） |
| [Agent 任務模板](templates/agent-task.md) | 1、3 | 交給 AI 代理執行的開發或自動化任務 |
| [摘要與文件審閱模板](templates/summary-review.md) | 1–2 | 會議紀錄、報告、合約等長文件的摘要與審閱 |
| [prompt-template.json](templates/prompt-template.json) | 全部 | 統一 JSON 結構；存檔、表單化、串接自動化 |
| [Prompt 產生器](../tutorial/) | 1–3 | 選層級、填欄位，即時產生 Markdown 與 JSON |

**依任務選模板**

| 我要… | 從這裡開始 |
| --- | --- |
| 整理、摘要、審閱一份或多份文件 | 摘要與文件審閱模板 |
| 請 AI 代理改程式、跑流程 | Agent 任務模板 |
| 分析程式碼、設計架構、做技術選型 | 程式與專案模板 |
| 做商業或投資類分析 | 投資分析模板（改寫 Persona 與 Depth 即可套用到其他產業分析） |
| 以上都不是 | 萬用模板，或直接用產生器 |

## 2. 模板卡：每個模板的中繼資料

模板沒有負責人與驗證日期，就無法判斷它是否還有效。每個模板開頭放一張模板卡：

| 欄位 | 說明 |
| --- | --- |
| 版本 | 語意化版本，如 `1.2.0`；改輸出格式時升主版號 |
| 狀態 | 草稿／審查中／已發布／已停用（見第 4 節） |
| 負責人 | 可以回答問題、核准修改的人或團隊 |
| 適用層級 | Level 1–3 中的哪幾層 |
| 適用／不適用 | 什麼情況該用、什麼情況不該用 |
| 驗證紀錄 | 用哪個模型、哪一天跑過測試案例，結果如何 |
| SLA 面向 | 本模板要達到的 Output SLA 面向（見第 6 節） |

**範例**

| 欄位 | 內容 |
| --- | --- |
| 版本 | 1.0.0 |
| 狀態 | 已發布 |
| 負責人 | 平台組 |
| 適用層級 | 1、3 |
| 適用／不適用 | 適用：交給 AI 代理的程式修改任務。不適用：需要人工判斷的架構決策 |
| 驗證紀錄 | 2026-11，主流推理模型，5 個測試案例全數通過 |
| SLA 面向 | 可執行性、格式合規、假設透明度 |

## 3. 撰寫規範

| 規則 | 做法 | 原因 |
| --- | --- | --- |
| 變數寫法 | 一律使用 `【變數名】`；選填加註「（選填）」 | 一眼看出要填的位置；不用雙大括號，避免與網站的 Liquid 語法及程式碼樣板衝突 |
| 資料區隔 | 用 XML 標籤包住資料：`<document>`、`<code>`、`<examples>` | 模型不會把資料誤當成指令 |
| 段落順序 | Persona → Task → Context → Format → Depth → Reasoning Mode → Decision → Stress Test → Self-check | 與 [prompt-template.json](templates/prompt-template.json) 欄位一一對應 |
| 限制條件 | 每條限制附上理由，不用「嚴禁」等強烈語氣 | 模型能推廣到沒列出的情況，見 [現代最佳實踐](05-modern-practices.md) |
| 範例 | 至少一個填好的實例，與空白模板放在同一頁 | 範例比說明文字更好懂 |
| 長度 | 只放這個任務需要的層級 | 模組越多，越難維護，也可能分散模型注意力 |

## 4. 生命週期

```
草稿 → 審查中 → 已發布 → 已停用
```

| 階段 | 進入條件 | 要做的事 |
| --- | --- | --- |
| 草稿 | 有人提出需求 | 寫好模板卡、空白模板、一個實例 |
| 審查中 | 草稿完成 | 準備 5 個以上測試案例；由負責人以外的人審查 |
| 已發布 | 測試案例達到 SLA | 合併到主分支，記錄於 [CHANGELOG](../CHANGELOG.md) |
| 已停用 | 有更好的模板，或用途消失 | 模板卡註明替代模板；保留一段時間再移除 |

**觸發重新驗證的時機**

- 改用新模型或模型大版本升級
- 使用者回報連續失敗
- 每季例行複審：檢查驗證紀錄是否超過 3 個月

## 5. 發布到工具：Prompt as Code

只放在文件裡的模板很少被用到。讓模板出現在使用者工作的地方：

| 載體 | 例子 | 適合 |
| --- | --- | --- |
| 專案說明檔 | `CLAUDE.md`、`AGENTS.md`、`.cursor/rules` | 每次對話都要套用的長期規則 |
| 可重用技能／指令 | Skills、slash command、IDE 的 prompt 檔 | 重複執行的任務，例如審查、摘要 |
| 共享助理 | Claude Projects、自訂 GPT、Gemini Gems | 不寫程式的同仁 |
| 工具協定 | MCP 伺服器提供的 prompts | 讓多種 AI 工具共用同一組模板 |
| API 或自動化 | 以 JSON 存檔，程式讀取後組成 prompt | 產品功能與排程流程，需搭配評估 |

**原則**

1. **單一來源**：模板只維護一份（例如本 repo），其他載體引用或自動同步，不要各自複製後各改各的。
2. **版本可追溯**：載體中註明模板名稱與版本，出問題時知道用的是哪一版。
3. **自動化要有評估**：進入產品或排程的模板，改版前必須跑過測試案例，見 [評估與迭代](07-evaluation-iteration.md)。

## 6. Output SLA（輸出品質標準）

事先定義「什麼叫做好」，才能驗收輸出、比較 prompt 版本。

| 面向 | 定義 | 檢查問題 | 建議量測方式 |
| --- | --- | --- | --- |
| **清晰度** | 讀者能快速理解 | 一句話版本能說清楚結論嗎？ | 人工、LLM-as-judge |
| **邏輯一致性** | 結論由前提推得、前後不矛盾 | 有沒有推理跳躍？ | 人工、LLM-as-judge |
| **可執行性** | 讀完知道下一步做什麼 | 有具體步驟與優先順序嗎？ | LLM-as-judge |
| **風險揭露** | 說明主要風險與不確定性 | 有提到最壞情境嗎？ | LLM-as-judge |
| **假設透明度** | 明列所依賴的假設與資料時間點 | 假設錯了結論會怎樣？ | LLM-as-judge |
| **事實可追溯** | 關鍵主張附來源與日期 | 每個數字找得到出處嗎？ | 人工抽查 |
| **格式合規** | 符合指定格式與長度 | JSON 能解析嗎？字數在範圍內嗎？ | 規則檢查 |
| **安全與隱私** | 不洩漏個資、機密或不當內容 | 輸出含有不該出現的資料嗎？ | 規則檢查 + 人工 |

不必每個模板都追求全部八項。在模板卡中選出 3–5 個最重要的面向，轉為 1–5 分評分表，用法見 [評估與迭代](07-evaluation-iteration.md)。

---

## 7. 團隊治理

1. **版本控管**：模板以檔案存在 repo，修改走 PR，並在 [CHANGELOG](../CHANGELOG.md) 記錄。
2. **一個欄位一個意思**：Markdown 段落與 JSON 欄位一一對應，避免同一概念有多種名稱。
3. **附上範例**：每個模板至少一個填好的實例。
4. **附上驗收方式**：模板卡列出 SLA 面向與測試案例。
5. **放進工具的脈絡**：常用規則寫進 AI 工具的專案說明檔，見 [Agent 與 Context Engineering](06-agent-context-engineering.md)。
6. **負責人與審查者分開**：修改由負責人以外的人審查。
7. **敏感資料不進模板**：模板與範例只用虛構資料；真實資料在使用時才放入 `<document>`。
8. **回報管道**：使用者發現模板失效時，用 issue 或 PR 回報，並附上輸入與輸出。

## 8. 選層提醒

依任務價值選擇層級的對照表見 [首頁](../README.md)。原則只有一條：**不要為了完整而完整**。低價值任務用 Level 1 就好，把 Level 3 留給真正要拍板的決策。
