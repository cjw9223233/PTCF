# Level 2｜進階控制層：Depth、Reasoning Mode、Constraint

> 適用於高價值分析：架構設計、技術選型、深度研究。建立在 [Level 1](01-core-ptcf.md) 之上。

Level 1 決定「做什麼」，Level 2 決定「想多深、怎麼想、邊界在哪」。

| 模組 | 控制的是 | 一句話 |
| --- | --- | --- |
| **Depth** | 洞察深度 | 要分析到哪一層？ |
| **Reasoning Mode** | 推理方式 | 用什麼方法推導？ |
| **Constraint** | 邊界條件 | 什麼不能做、必須符合什麼？ |

---

## 1. Depth（深度層級）

明確指定分析層級，否則模型通常停在「結構性說明」。

| 類別 | 層級選項 |
| --- | --- |
| 通用 | 基礎說明 → 結構性分析 → 底層邏輯 → 第一性原理 |
| 系統 | 系統思考（找因果循環）、可擴展性分析 |
| 風險 | 風險分析（最壞情境）、機率思考（不確定性） |
| 策略 | 槓桿思維（小投入大回報）、博弈思考（利益衝突） |
| 技術 | 程式邏輯層 → 架構層 → 系統設計層、技術債評估 |
| 讀者 | 初學者友善（比喻 + 步驟）↔ 業界專家級（術語 + 最佳實踐） |

**寫法**：「請分析到系統設計層，並評估可擴展性；讀者是有 3 年經驗的工程師。」

## 2. Reasoning Mode（推理模式）

| 模式 | 什麼時候用 | 寫法 |
| --- | --- | --- |
| **Few-shot**（少樣本） | 想要特定風格、格式或判斷標準 | 提供 2–5 個輸入 → 輸出範例 |
| **Chain of Thought**（逐步推理） | 多步驟計算、邏輯推導 | 見下方「推理模型時代的 CoT」 |
| **First Principles**（第一性原理） | 想跳脫慣例、重新設計 | 「先拆出不可再分的基本事實與限制，再從這些推導方案」 |
| **Scenario Simulation**（情境模擬） | 評估策略、規劃風險 | 「分別模擬樂觀、基準、悲觀三種情境」 |

### 推理模型時代的 CoT

現在多數主流模型（例如具備 extended thinking 的 Claude、OpenAI 的 o 系列與 GPT-5 系列）會在回答前**自行思考**。因此：

- **推理模型**：不需要寫「請逐步思考」。把力氣花在說清楚**目標、限制與理由**；需要更深入時，用「請仔細考慮邊界情況」或調高思考強度（effort／thinking budget）。
- **一般模型、或你需要看到推理過程**：仍可明確要求，並把推理與答案分開，方便檢查：

  ```text
  請先在 <thinking> 中列出推理步驟，再在 <answer> 中給出結論。
  ```

- 對推理模型下過度細碎的步驟指示，反而可能限制它的發揮；給目標與判準，讓它決定步驟。

### Few-shot 寫法

- 範例要**多樣**，涵蓋不同情況，避免模型只學到表面特徵。
- 用標籤包住範例，和真正的任務分開：

  ```text
  <examples>
  <example>
  <input>if (x == 'active') { doA(); } else { doB(); }</input>
  <output>改用對照表或策略模式取代多重 if-else，便於擴充新狀態。</output>
  </example>
  <example>
  <input>一個 500 行的結帳函式，同時呼叫 API 與更新 UI</input>
  <output>將資料請求、業務邏輯與 UI 更新拆成三層。</output>
  </example>
  </examples>
  ```

- 範例過於一致時，模型會直接照抄格式甚至內容；若只要「風格參考」，請明說。

## 3. Constraint（限制條件）

| 類型 | 範例 |
| --- | --- |
| 效能 | P99 延遲 < 200ms |
| 安全 | 不可把個資寫入 log |
| 相容性 | 需支援 Java 11 |
| 成本 | 每月雲端費用 < US$500；不使用商業資料庫 |
| 語言與用字 | 使用繁體中文與台灣慣用術語 |

**寫法要點**

1. **附上理由**：「使用繁體中文，因為讀者在台灣」比「嚴禁簡體字」更有效，模型能推廣到沒列出的情況（例如用詞習慣）。
2. **正向描述**：說「要做什麼」優於只說「不要做什麼」。
3. **避免過度強調**：新一代模型對指令很敏感，全大寫、「絕對」「嚴禁」容易讓它在不相關的地方也過度套用。一般語氣即可。

## 範例：高流量 API 架構（Level 1 + 2）

```markdown
Persona：資深系統架構師

Task：設計可擴展的高流量 API 架構

Context：
- 每日 100 萬請求，尖峰為平均的 5 倍
- 部署於 Kubernetes，資料庫為 PostgreSQL

Format：架構圖（文字描述或 Mermaid）+ 條列說明

Depth：系統設計層，含可擴展性分析
Reasoning Mode：先用第一性原理拆出負載特性，再推導架構
Constraint：
- 成本需控制（新創預算有限）
- 不使用商業資料庫（授權費超出預算）
```

預期得到：負載拆解、快取策略、水平擴展方案與可能瓶頸。
