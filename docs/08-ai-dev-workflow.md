# 與 AI 協作開發流程

> 對象：用 AI 代理寫程式的專案負責人與開發者（含新手）。說明怎麼請 AI 協助、PR 與審查怎麼走、哪些事一定要人工核准。指令以 Claude Code 為例，其他工具多有類似功能。

---

## 0. 一頁總結

| 原則 | 做法 |
| --- | --- |
| AI 是「有權限的資深同事」 | 寫得快，但**驗收與核准是你的責任** |
| 動手前先有乾淨的 git 狀態 | 先 commit，再請 AI 改；改完看 `git diff` |
| 重要規則寫進專案說明檔 | 讓每次對話自動遵守（見 [Agent 與 Context Engineering](06-agent-context-engineering.md)） |
| 大改動先規劃再做 | 先看計畫，你核准才動手 |
| 審查三件套 | 找 bug → 簡化 → 安全審查 |
| 危險動作維持人工核准 | 刪檔、push、merge、發版 |
| 如實回報 | 要求 AI 說明「沒驗證到的部分」 |

**最重要的一條**：先 commit、改完看 diff。AI 偶爾會把已有內容的檔案當成新檔覆寫；有 git，這類問題幾秒內就能發現並還原。

---

## 1. 開始之前

- 確認 `.gitignore` 排除執行結果、暫存檔、含個資或本機路徑的報表，避免私有資料進入版控。
- 含敏感資訊的 repo 建成 **private**。
- Commit 訊息使用慣例前綴：`feat:` 新功能、`fix:` 修 bug、`docs:` 文件、`test:` 測試、`refactor:` 重構、`chore:` 雜項。

---

## 2. 整體流程

```
立規矩 → 想清楚 → 開分支 → 實作 + 測試 → 審查 → commit / PR → 合併 → 維運
```

| 階段 | 你做什麼 | 請 AI 做什麼 |
| --- | --- | --- |
| 1. 立規矩（一次性） | 建立專案說明檔（Claude Code：`/init`） | 記錄建置與測試指令、架構、專案慣例與禁忌 |
| 2. 想清楚 | 用規劃模式描述需求 | 先讀程式碼、提出計畫與風險，**你核准才動手** |
| 3. 開分支 | 一個需求一條分支 | 動手前提議分支名（如 `feat/csv-export`）；並行工作用不同 session 或 worktree，避免互相覆蓋 |
| 4. 實作 + 測試 | 看 diff、看測試結果 | 改程式、補測試、跑測試，列出沒驗證到的地方 |
| 5. 審查 | 執行審查指令 | 找 bug、簡化、查安全問題 |
| 6. 提交 / PR | 核准 commit 與 push | 撰寫 commit 訊息與 PR 說明、開 PR |
| 7. 維運 | 決定頻率 | 排程檢查、整理報表 |

---

## 3. 常用指令（以 Claude Code 為例）

### 開發與審查

| 指令 | 用途 | 建議時機 |
| --- | --- | --- |
| `/init` | 建立 `CLAUDE.md` | 新專案第一件事 |
| `/code-review` | 審查目前改動的正確性問題；可加等級（`low`～`max`）、`--fix` 直接修、`--comment` 貼成 PR 行內留言 | 每個 PR 前，平常用 `high` 即可 |
| `/simplify` | 找重複、可簡化與效率問題並修正 | 功能完成後收尾；只管品質，不抓 bug |
| `/security-review` | 針對待提交變更做安全審查 | 動到權限、刪除、外部輸入處理時必跑 |
| `/run` | 啟動並實際操作專案 | 確認改動真的有效，而不只是測試通過 |

### 自動化與設定

| 指令 | 用途 |
| --- | --- |
| `/schedule` | 建立定期執行的雲端任務 |
| `/loop` | 依間隔重複執行某個提示或指令 |
| `/update-config` | 設定 hooks、權限、環境變數；**必須每次都發生**的檢查用 hook，口頭交代不保證 |
| `/fewer-permission-prompts` | 建議哪些唯讀指令可預先允許，減少重複確認 |

## 4. PR 流程

### 一個需求的標準走法

```
git switch -c feat/xxx       # 或請 AI 在動手前提議分支
  …請 AI 實作 + 跑測試…
/code-review high            # 審查
/simplify                    # 收尾
/security-review             # 動到敏感邏輯時必跑
git diff                     # 你自己看一遍
commit → push → 開 PR → 等 CI → 你核准 → merge
```

- PR 開出後可交由 AI 處理 CI 失敗、合併衝突與審查留言，但**不要讓它自動 merge**，除非你明確要求。

### 好的 PR

| 項目 | 要求 |
| --- | --- |
| 大小 | 一個 PR 只做一件事；超過約 400 行變更就拆 |
| 標題 | 慣例前綴 + 一句話，如 `fix: 匯出時忽略空白列` |
| 說明 | 為什麼改、改了什麼、**怎麼測**、**沒測到什麼**、風險與還原方式 |
| 檢查 | 測試全過；動到敏感邏輯附安全審查結論 |
| 還原 | 說明回滾方法（通常是 `git revert <commit>`） |

## 5. 下指令範本

| 情境 | 建議說法 |
| --- | --- |
| 新功能 | 「用規劃模式：新增 XX。先列出影響的檔案與風險，等我核准。」 |
| 修 bug | 「先重現問題 → 寫會失敗的測試 → 修 → 全部測試通過。」 |
| 動到危險邏輯 | 「這次只改預覽輸出，不要動實際執行的路徑；改完跑安全審查。」 |
| 提交前 | 「看 `git diff`，逐檔說明變更，並列出沒驗證到的地方。」 |
| 不確定時 | 「先別動手，告訴我你打算改哪些檔、為什麼。」 |
| 接手陌生程式 | 「讀 README 與主要進入點，用 5 句話說明資料流，並指出最容易壞的 3 個地方。」 |
| 寫文件 | 「依目前程式碼更新 README 的參數表，不要改其他段落。」 |

**好的需求包含**：目標、範圍（改哪些、不改哪些）、驗收方式、限制。

---

## 6. 護欄清單

- **先 commit 再讓它改**；改完看 `git diff` 再 commit。
- 要求**如實回報**：沒涵蓋的測試、沒驗證的部分、做了哪些假設。
- **危險動作維持人工核准**：刪檔、push、merge、發版；不要為了方便放寬預設的確認步驟。
- **不要貼密碼、金鑰、客戶資料**進對話或 commit。
- 對 AI 的輸出保持懷疑：指令與路徑先看過再執行。
- 高強度審查（如 `/code-review ultra`、`max`）花費較多，大改動才用。
- AI 看不到你的螢幕與機器狀態，除非它實際執行過；「應該可以」不等於「驗證過」。

## 7. 常見問題

| 問題 | 回答 |
| --- | --- |
| AI 改壞了怎麼辦？ | 用 `git diff` 檢視；`git restore <檔案>` 或 `git revert <commit>` 還原。這就是要先 commit 的原因 |
| 可以直接叫它「全部處理好」嗎？ | 小事可以；大事先規劃。需求越模糊，越需要你驗收 |
| 審查抓到很多項目，都要修嗎？ | 不必。依嚴重度排序，高信心的正確性問題先修，其餘記錄成 issue |
| 它說「測試通過」就能放心嗎？ | 看測試涵蓋範圍；測試沒涵蓋的部分要手動驗證 |
| 怎麼讓團隊遵守同樣規則？ | 把規則寫進專案說明檔並 commit；必須每次發生的檢查用 hook 或 CI |
