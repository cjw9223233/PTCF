# Level 1｜核心層：PTCF 四要素

> 適用於約 80% 的日常任務。先把這一層寫好，再考慮加其他層。

**有效輸出 = Persona × Task × Context × Format**

四個要素是相乘關係：任何一項空白，輸出品質都會明顯下降。其中最常被省略、也最影響結果的是 **Context**。

---

## 四要素總覽

| 要素 | 核心問題 | 控制的是 | 少了它會怎樣 |
| --- | --- | --- | --- |
| **Persona**（角色） | 用什麼身份與視角思考？ | 專業框架、用語、語氣 | 回答泛泛、口吻不對 |
| **Task**（任務） | 要完成什麼？ | 行為方向 | 答非所問 |
| **Context**（情境） | 在什麼條件下？ | 資訊完整度 | 模型只能猜，容易幻覺 |
| **Format**（格式） | 怎麼呈現？ | 可用性 | 內容對但無法直接使用 |

---

## 1. Persona（角色）

定義模型要用的專業視角與表達方式。

| 類型 | 範例 |
| --- | --- |
| 技術 | 資深後端工程師、系統架構師、專案經理 |
| 金融 | 證券分析師、CFA／CIIA |
| 顧問 | 資深管理顧問、品牌顧問 |
| 教學 | 初學者友善講師 |
| 思考方式 | 第一性原理拆解者、反方辯證者 |
| 健康 | 營養師、運動教練 |

**寫法**

- 「你是一位資深系統架構師，熟悉 Kubernetes 與 PostgreSQL。」
- 加上**對象**往往比加上頭銜更有效：「讀者是剛轉職的新手工程師。」

> **注意**：Persona 主要影響用語、深度與觀點，不保證答案更正確。事實正確性靠的是 Context（提供資料）與 Level 3 的驗證。

---

## 2. Task（任務）

用動詞明確說出要做什麼；有多件事時編號列出。

| 類型 | 常見動詞 |
| --- | --- |
| 摘要整理 | 總結、抽取重點、列 5–10 個關鍵字、產出簡報摘要 |
| 改寫優化 | 潤飾、讓邏輯更清楚、修正英文 |
| 分析拆解 | 找底層邏輯、用第一性原理拆解、評估論點是否成立、舉實例 |
| 批判挑戰 | 挑戰我的觀點、提出不同角度 |
| 教學 | 用比喻 + 步驟 + 常見誤區講解 |
| 專案解析 | 說明專案用途、技術棧、進入點、資料夾結構、架構圖 |
| 程式 | 說明並註解程式碼、重構、找出可強化的環節 |
| 決策 | 比較方案、給出建議與優先順序（見 [Level 3](03-decision-validation.md)） |

**寫法要點**

- 一個 Task 只放一個主要目標；目標不同時拆成多次對話或 prompt chaining（見 [現代最佳實踐](05-modern-practices.md) 的 Prompt Chaining）。
- 說明**為什麼**要做這件事，模型會據此自行判斷細節。

---

## 3. Context（情境）

提供模型無法自己知道的資訊。好的 Context 回答四件事：

| 項目 | 範例 |
| --- | --- |
| **背景** | 這是電商結帳的 legacy code；團隊 30 人，目前使用 SVN |
| **目標** | 提升可測試性；三個月內導入 CI/CD |
| **限制** | 不能使用商業資料庫；使用繁體中文 |
| **資料** | 程式碼、文件、財報、會議紀錄 |

**資料要和指令分開**，建議用 XML 標籤包起來：

```text
<document>
（貼上原始資料）
</document>
```

舊版使用的 `<<< >>>` 也可以，但標籤能命名、能巢狀，多份資料時更清楚。詳見 [現代最佳實踐](05-modern-practices.md)。

---

## 4. Format（格式）

規定輸出長什麼樣子，讓結果能直接使用。

| 需求 | 寫法 |
| --- | --- |
| 快速閱讀 | 條列式、表格 + 一段摘要 |
| 文件 | Markdown、README.md |
| 程式處理 | JSON（API 情境建議改用結構化輸出，見 [現代最佳實踐](05-modern-practices.md)） |
| 視覺化 | 流程圖、架構圖（文字描述或 Mermaid） |
| 長度 | 150 字內、一句話版本 |

---

## 範例

### 範例 A：最小可用（四行就夠）

```markdown
Persona：品牌顧問
Task：撰寫專業的 LinkedIn 自我介紹
Context：10 年後端經驗，擅長架構設計，正在找技術主管職
Format：150 字內，專業但不生硬，繁體中文
```

這類低風險任務不需要加 Depth、Decision 或 Stress Test。

### 範例 B：程式重構

```markdown
Persona：資深後端架構師

Task：
1. 分析下方 Controller 的問題
2. 提出重構建議並附重構後程式碼

Context：
- Java Spring Boot 專案
- Controller 超過 800 行，同時處理驗證、業務邏輯與資料存取
- 目標是提升可維護性與可測試性

Format：
- 條列式問題分析（標註違反的設計原則）
- 重構前後對照

<code>
（貼上程式碼）
</code>
```

## 檢查清單

- [ ] Persona：有指定視角，必要時說明讀者是誰
- [ ] Task：有明確動詞，多件事已編號
- [ ] Context：背景、目標、限制、資料都交代了
- [ ] Format：模型知道該輸出什麼形式與長度
